Overview & Deployment Models

Pieria is two things: a curation brain you run once (a small Docker app), and any screen you point at it. Add art, and it plays beautifully — with cinematic pans, museum placards, and a phone remote.

How it works

The server holds your library, generates metadata, and decides what shows next. Each screen just opens a URL (or, for e-ink, fetches an image). The brain runs in one place; screens are cheap and disposable.

Deployment models — pick what fits

It's a versatile setup. The same server supports any mix of these at once:

Core

Run the brain anywhere

Docker on a server, NAS, mini-PC, or an old laptop. Then point any screen at it. This is the foundation for every model below.

Simplest single frame

All-in-one Pi

Server and display on one Raspberry Pi. Flash a card, hang it behind a monitor — one self-contained art frame.

Scales to a whole home

Thin-client Pi → server

One server curates; cheap Pis in each room just display. Add rooms by flashing another card.

No extra hardware

Any browser / Smart TV

Point a TV browser (or Fully Kiosk) at the display URL. Great for a TV you already own.

Low power

e-ink / "dumb" frame

Battery e-ink and DIY frames fetch a server-rendered, dithered image on a wake schedule. No browser needed.

One server, many screens

Multi-display

Give each screen a unique display ID; the phone remote targets any of them independently.

New here? For a hang-and-forget frame, the easiest path is to flash the appliance image and set it up from your phone — no terminal. To run the curation server yourself, start with Quick Start (Docker).

Quick Start

The fastest path: run the server with Docker, then open the dashboard. No config files required.

Prerequisites

  • Docker + Docker Compose (most installs include Compose).

Launch

git clone https://github.com/pieria-art/Pieria.git
cd Pieria
docker compose up -d --build

That's it — no .env needed. The app boots with starter art already curated.

Open it

  • Admin Dashboard — http://localhost:8000/admin (upload, browse the catalog, manage collections)
  • Main Display — http://localhost:8000/ (point your TV/monitor browser here)
  • Mobile Remote — http://localhost:8000/remote (control from your phone)
Prefer a dedicated frame? Flash a Raspberry Pi instead and it boots straight into the fullscreen display — see the Raspberry Pi Appliance below.

Adding Art

Three ways to fill your walls. Curated Art needs no AI key at all — only auto-analysis of your own uploads does.

1. Curated Art — your collections + official packs

The 🏛️ Curated Art tab is the home for the art on your walls. At the top, a search box (with title/artist autocomplete) finds a specific piece; below it, Your Collections is a grid of collection tiles for adding whole collections at once.

  • Collections you own — each is a downloaded, signature-verified pack that plays fully offline. A tile shows its cover, work count, size, and a Verified badge; Remove uninstalls it and reclaims the disk (works shared with another collection, and your own photos, are kept).
  • Official packs you can add — dimmed tiles tagged Official. Click Download and the whole collection downloads once, verifies against its signature, and becomes yours — no per-piece hunting, and owning the art means it never rots or disappears.
  • ➕ Subscribe — paste a publisher's collection URL to index it as a Community tile alongside the official packs.

Looking for one specific piece? Use the search box up top. The 🏛️ Curated catalog scope searches instantly across your collections — an already-owned work shows an Added ✓ tag instead of a duplicate. Come up short and a clear “Search live museums →” prompt widens the very same query to 🌐 Live museum search: the Met, Art Institute of Chicago, Cleveland, Rijksmuseum, SMK, NASA (space photography), and Wikimedia Commons (the broadest public-domain pool). Pick which repositories to search under Advanced sources. Click Review on a live find and its card expands right there into an editable placard — the AI writes the details in as you watch, and you Approve & Publish (or Discard) without ever leaving the page. NASA and Wikimedia need no key; Wikimedia results are filtered to public-domain works ≥2000px.

2. Upload your own

Drag & drop images into the Full Library or a collection. If a model is connected, each upload is auto-analyzed (title, a 2-sentence blurb, tags) and lands in the Review Queue; if not, you simply fill in the details yourself there and Approve & Publish. Either way you stay in control — nothing reaches your screens until you approve it.

Review Queue: every new upload waits here so AI guesses never hit your walls unchecked. Edit any field, add an AI Guidance hint and Regenerate (if a model is connected), or just type the details and publish.

Put your own photos up — My Photos (Studio)

For family, pet, and vacation photos there's a separate, phone-friendly front door at /studio. Add or snap photos, give each a caption (or tap ✨ Suggest for an AI one in a warm photo-album voice), tap the photo to set its focus point, and they go straight to a My Photos collection — no review queue, no museum jargon, just a clean caption on the wall. Every photo you've added shows in a gallery below the uploader, grouped by album — tap any one to re-edit its caption, date, or focus point anytime. iPhone photos work as-is: Apple's HEIC format is converted to a standard image automatically on upload.

Privacy: your photos stay on your server — never uploaded to anyone's cloud, never indexed. AI captioning is opt-in; if your AI Engine points at a local model (Ollama / LM Studio) the photo never leaves your network, and the Studio tells you which case you're in before you use it.

3. Subscribe to a collection (beta)

Under 🏛️ Curated Art, the ➕ Subscribe tile takes a publisher's collection URL and indexes their art alongside the official packs, tagged Community (added by URL) or Verified (a signed feed whose publisher is in our registry); official packs show as Official. We index pointers only — images stay on the publisher's server — and every feed is safety-checked and validated before it's added. Manage your feeds (Sync to refresh, Remove to unsubscribe) under Settings → 🌐 Subscriptions; already-added artworks stay in your library.

Publishing your own? Open Publisher Studio to author and sign a collection of your own hosted images, then host the exported manifest.json anywhere and share its URL. Prefer the command line? Use python -m tools.build_manifest. Full walkthrough: How to publish (the Manifest v2 schema).

Hosting the catalog remotely (grow it without rebuilding)

The curated catalog ships bundled inside the app. To expand or update it without rebuilding the image, host the catalog files on any static URL and point the app at them in Settings → 📚 Catalog Source. The app fetches the remote index.json + per-collection files and falls back to the bundled catalog automatically if the URL is ever unreachable.

  1. Generate the files. Run the offline builder python -m tools.build_catalog — it writes index.json plus one <collection>.json per collection into static/catalog/.
  2. Host them on any static host — a GitHub repo's raw URL, an S3/R2 bucket, Netlify, or any plain web server. Keep index.json and the per-collection files together under one base path.
  3. Point the app at the base URL (the folder, not index.json itself) in Settings → 📚 Catalog Source, then Test & Save. It confirms the URL and reports how many collections it found.
Note: a remote catalog only changes where the list comes from — images are still hotlinked from wherever the manifest points, and the full-resolution file downloads only when you Add a piece (same as the bundled catalog). Reset to bundled clears it anytime.

Editing & Organizing

Collections vs. Galleries — the one distinction to know. Collections are what you have — art you own (an official pack you downloaded, or a feed you subscribed to), managed under 🏛️ Curated Art. Galleries are what you show — a sequence that plays on a screen, with its own order, timing, and pan-and-zoom, under 🖼️ Galleries. Downloading a Collection creates a matching Gallery to get you started (it's marked “from your … Collection”); build your own by mixing works from any Collection. Deleting a Gallery removes only that show — the art stays in your library and Collections. Removed a work from a seeded gallery by mistake? ↻ Restore (on its "from your … Collection" line) re-adds the Collection's works. And removing a Collection reclaims only its art — anything you added to its gallery stays in your library.

Click any artwork's thumbnail (or its Edit button) in the Library or a Gallery to open the full-screen Edit screen — one place to crop, set the focus point (drag the ◉; it's what Ken Burns and e-ink frames keep in view), edit the placard title/description, and — with an AI model connected — ✨ Re-enrich. Your own photos open a simpler caption-and-date version. Save commits everything at once; Delete (Library) or Remove (from a Gallery) lives there too.

Working in bulk

To move or clear out many pieces at once, hit ☑ Select in the Library or a Gallery, tap the works you want, then use the action bar to Add to a Gallery, Remove them from the current Gallery, or Delete them from the library. The Add from Library picker is multi-select too — tick everything you want and add it in one go. The same ☑ Select mode is in the Review Queue (Approve & Publish a batch at once) and on the Curated Art search results (Add selected to your library).

Connecting a Model (AI Engine)

A model is optional — Museum Art (curated + live search) and manual metadata all work without one. Connect a model to unlock auto-curation: metadata generation on upload, Wikipedia-grounded enrichment, and smarter search.

Open Admin → ⚙ Settings → 🧠 AI Engine, pick a provider, connect, and click Test & Save — the key is validated live before it's stored, and takes effect within seconds (no file editing, no rebuild).

  • Google Gemini — free tier is plenty for personal use. Get a key →
  • OpenAI (GPT-4o) and Anthropic (Claude) — paste your provider key.
  • OpenRouter — one-click Sign in with OpenRouter (no key to copy), then reach every major model through one account.
  • Local / Ollama / LM Studio — point the Base URL at your own OpenAI-compatible server (inside Docker, use host.docker.internal instead of localhost); no key needed.
One backend for everything: every provider is reached through a single OpenAI-compatible endpoint, so configuration is just base URL + key + model. The Advanced section lets you use a separate cheaper/faster model for search classification, override the Base URL, or set a temperature.

Note: OpenRouter's one-click sign-in needs a secure context — it works over HTTPS or http://localhost, but not a plain http://<LAN-IP> address (paste an OpenRouter key there instead). See HTTPS.

Prefer a file? Optional .env fallback

You can seed a default key before first run with a .env in the project root (the AI Engine panel overrides it when set):

# Optional fallback
GEMINI_API_KEY=your_free_key_here

The Display & Rendering Modes

Point any screen's browser at http://SERVER:8000/?display=living_room. The display ID names that screen so the remote can target it. The display paints automatically and stays awake — no browser chrome, no manual refresh.

Rendering modes

  • Ken Burns (ken-burns) — slow cinematic pan & zoom, anchored on each piece's focus point so faces and key subjects stay in frame (off-center subjects get a gentler zoom; centered ones get the full drift).
  • Static crop (static-crop) — a fixed, user-defined crop (set per-artwork in the admin).
  • Contain matte (contain-matte) — the whole piece, letterboxed on a blurred matte.

Set a mode globally, per-collection, or per-screen via the URL parameters. Each piece shows an auto-generated museum placard (title, artist, blurb) and a QR code for details.

Image resolution & first-display loading

Museum originals can be enormous — a single public-domain scan is often 40–110 MB and 150+ megapixels. That's far more than any screen shows, and more than a low-power browser (a Raspberry Pi, a TV stick) can decode and paint. So the display loads a resolution-capped copy (up to 8K on the long edge — still well beyond 4K, with headroom for cropping and Ken Burns zoom), while the full-resolution original stays on disk untouched.

First time a brand-new piece appears, it may take a few seconds to paint on low-power hardware — the capped copy is generated once, on demand, then cached permanently, so every later showing is instant. With a normal rotation (a piece stays up for minutes), you'll never notice it; it's only visible if you flip through many never-seen pieces rapidly. Restarting or rebuilding the server keeps the cache.

The Mobile Remote Control

Open /remote on any phone on the same network — a no-refresh console for every screen.

  • WebSocket routing: changes hit the targeted TV instantly, with no page refresh.
  • Target selection: the "Target Display" dropdown lists every screen as soon as it's opened in a browser. A low-power panel that sleeps between refreshes stays listed, marked asleep — it's still showing art, it just can't take a command until it next wakes.
  • Instant actions: Next/Previous and a "Show Placard on Screen" button to throw the placard up on the display itself.
  • Read placard: tap it to read the full placard — artist, date, medium, the write-up and tags — on your phone. This is how e-ink gets a placard at all: an e-ink panel renders the artwork only, so the phone in your hand is the wall label.

URL Parameters Reference

Append these to a display URL (e.g. http://SERVER:8000/?display=tv_01&rotate=true) to override behavior for one screen.

ParameterDescriptionExample
displayUnique ID for this screen so the remote can target it. Defaults to default.display=living_room
modeRendering mode: ken-burns, static-crop, contain-matte.mode=contain-matte
cycle_timeSeconds between artwork transitions.cycle_time=60
shuffleRandomize playback order: true / false.shuffle=true
rotateRotates the whole display -90° for TVs mounted vertically in landscape mode.rotate=true
placard_waitSeconds after a new image loads before the placard slides in.placard_wait=5
placard_showSeconds to keep the placard visible on its initial entrance.placard_show=20
placard_manualSeconds to display the placard when triggered by the remote.placard_manual=15

Raspberry Pi Appliance (Recommended for TVs)

A dedicated Raspberry Pi boots straight into the full-screen display — no browser chrome, no manual URL entry, no third-party kiosk app. There are two ways to get one: flash the pre-baked image (no terminal at all) or build it yourself with the provisioner. (A Pi 4 is plenty for display-only; a Pi 5 is recommended if the box also runs the server.)

The easy way — flash the pre-baked image

The all-in-one appliance image sets itself up from your phone. You never open a terminal or edit a file:

  1. Download pieria-<version>.img.xz from the Releases page.
  2. Flash it with Raspberry Pi Imager or Balena Etcher — no OS-customisation needed (leave "Edit Settings" alone).
  3. Boot the Pi. The screen shows a setup card. From your phone, join the open Pieria-Setup Wi-Fi network — a setup page opens on its own (captive portal).
  4. Set it up: pick your Wi-Fi from the list, name the display (it becomes <name>.local), choose orientation (with a live preview), confirm. The Pi joins your network, downloads its first gallery, and paints — unattended.
It won't strand you. Mistype the Wi-Fi password or interrupt setup and the box re-opens the Pieria-Setup hotspot on the next boot instead of showing a dead screen — so you always get another try from your phone. Each unit generates its own network name and its own security identity on first boot; nothing is shared between units.
Updates, no SSH. When a newer release ships, Admin → 🩺 Devices → Appliance Maintenance shows it with release notes and a one-click Update — the box pulls it and rebuilds itself. You choose when; nothing installs on its own.

Build it yourself (or a thin-client)

To build the image from scratch, roll your own for another board, or set up a display-only thin client (this Pi shows art; a server elsewhere curates), run the provisioner on a fresh Raspberry Pi OS Lite (64-bit, Bookworm). Flash it with Imager (set a hostname, SSH, and Wi-Fi under Edit Settings), SSH in, then:

git clone https://github.com/pieria-art/Pieria.git
# all-in-one (server + display on this box):
sudo ALL_IN_ONE=1 EINK_ENABLED=1 Pieria/deploy/appliance/install.sh
# ...or display-only thin client (server lives elsewhere): omit ALL_IN_ONE.

This installs cage + Chromium as a kiosk, launches it on boot, disables screen blanking, ensures avahi-daemon (so <hostname>.local works), and (all- in-one) installs Docker and runs the server on the same Pi. To turn a provisioned box into a distributable image, see docs/image-build.md.

Configure a thin-client display

Finding your server's address For a thin client, SERVER_URL is wherever your Pieria server runs — not this Pi. To find it:
  • Open the admin (Settings → 📡 This Server) on the server box — it shows the exact address to copy.
  • Or on the server run hostname -I for its LAN IP (e.g. 192.168.1.50) → http://192.168.1.50:8000.
  • Or use its hostname: http://<server-hostname>.local:8000 (works on most home networks via mDNS).

Edit pieria.conf on the card's boot partition (visible on any computer — no SSH needed), then reboot:

SERVER_URL=http://192.168.1.50:8000   # your Pieria server
DISPLAY_ID=living_room                # unique name shown in the remote
MODE=                                 # optional: ken-burns|static-crop|contain-matte
CYCLE_TIME=                           # optional: seconds per image

The Pi comes up full-screen on the Canvas. While the server is still starting (or not yet reachable), the screen shows a boot splash with the admin URL, this display's <hostname>.local, and its IP — so you can read the address right off the wall instead of hunting the DHCP lease — then it switches to the art automatically once the server answers.

Device Health (all-in-one only)

On an all-in-one box, a 🩺 Devices tab appears in the admin sidebar with live health for the machine running Pieria — CPU load, temperature, memory, free disk, uptime, Pi power/throttle (under-voltage) state, and the displays currently being served.

This tab is shown only in all-in-one mode. A thin-client (display-only) Pi runs no server, so there's nothing to measure there — its admin is served by your central server, whose own Devices tab reflects that box. Under-voltage/throttle needs the host vcgencmd, gathered by a small sd-metrics timer the installer sets up; where it isn't available the field reads unavailable.

Can't reach the box? Use http://<hostname>.local:8000/admin (the hostname you set in Imager) instead of hunting for the IP. If .local doesn't resolve (some Android devices), find the Pi's address in your router's client list. Full reference & troubleshooting: deploy/appliance/README.md in the repo.

e-ink & "Dumb" Frames (Image API)

Low-power e-ink and "bring-your-own-server" frames don't run the browser display at all — they just fetch a server-rendered image on a wake schedule. This covers DIY ESP32 + Waveshare panels, Pimoroni Inky Impression, a TRMNL in BYOS mode, or any device (even a tiny script) that can perform an HTTP GET on a timer. The server crops to your panel size and Floyd–Steinberg-dithers to the device palette.

The endpoint

GET /display/{display_id}/current.png?playlist=Masterpieces&w=1600&h=1200&palette=spectra6
ParameterValues
display_idA unique name for this frame (path segment)
playlistCollection name. Omit it and the frame falls back to what this display last played, then your default collection, then the first collection that actually has art in it.
w / hYour panel's pixel dimensions
palettespectra6, acep7, gray4, gray16
fitcover (fill, default) or contain (letterbox)
formatEnd the path in .png (default) or .bmp (firmware without a PNG decoder)

Each request advances to the next image, so the frame's wake interval becomes its rotation. The response's X-Refresh-After header tells the frame how many seconds to deep-sleep before fetching again.

How to set up a generic "dumb terminal" frame

Any device that can GET a URL on a timer works. The pattern is always the same: wake → GET the image sized for your panel → display it → sleep for X-Refresh-After seconds. A Raspberry Pi driving any panel from the framebuffer can do it in a few lines (set SERVER to your server's address — see Finding your server's address):

#!/bin/sh
SERVER=http://192.168.1.50:8000
DISPLAY_ID=hallway
PALETTE=spectra6          # spectra6 | acep7 | gray4 | gray16
W=1600; H=1200            # your panel size

while true; do
  # Fetch the next image (headers -> /tmp/h, body -> /tmp/art.png)
  curl -s -D /tmp/h -o /tmp/art.png \
    "$SERVER/display/$DISPLAY_ID/current.png?w=$W&h=$H&palette=$PALETTE"

  # Show it (framebuffer example; swap in your panel's render command)
  fbi -T 1 -noverbose -a /tmp/art.png

  # Sleep for the server-suggested interval (fallback 300s)
  SECS=$(awk -F': *' 'tolower($1)=="x-refresh-after"{print $2+0}' /tmp/h)
  sleep "${SECS:-300}"
done

On a true e-ink microcontroller (ESP32 + Waveshare, Inky, etc.) the same flow runs once per wake: connect Wi-Fi → GET .../current.bmp?... → push the bytes to the panel → read X-Refresh-After → deep_sleep() for that many seconds. Request .bmp if your firmware can't decode PNG.

Already-shipping example: a TRMNL in BYOS mode already polls a server, downloads an image, and deep-sleeps for a refresh interval — point its server URL at this endpoint and it works as-is.

HTTPS (optional)

For a home LAN, plain HTTP is usually fine — the display path carries no secrets, and the "Not secure" label is mostly perception. HTTPS earns its keep in two cases: you expose the admin beyond your trusted network (so pasted API keys aren't sent in the clear), or you want OpenRouter's one-click sign-in (which needs a secure context).

Turn it on

docker compose --profile tls up -d     # adds an HTTPS proxy on :443; the app stays on :8000

This runs a Caddy reverse proxy in front of the app. Browser-trusted HTTPS on a LAN needs either a real domain (Caddy fetches a Let's Encrypt cert automatically), or Caddy's internal CA — which means installing its root certificate on each device that opens the admin. Full step-by-step (including the cert-trust commands) is in the repository README.md → "Enabling HTTPS".

Keep kiosks on HTTP. Don't point a TV/Pi/e-ink screen at an internal-CA HTTPS URL — they can't accept the certificate. Reserve HTTPS for the human-facing admin/remote you open yourself; displays stay on plain http://.

Hardware & Kiosk Best Practices

For a seamless "Museum" experience, your display should behave like a native appliance rather than a browser window. The recommended way to get there is the Raspberry Pi Appliance above — the options below are for reusing an existing TV stick instead.

Which board should I buy, and how much RAM? See the Hardware Profile — validated RAM/storage sizing by output type (TV, e-ink, satellite), soak-tested thermals, and current board prices.

Bring-your-own TV stick (fallback)

  • Android / Fire OS: Fully Kiosk Browser locks the TV to a URL, hides toolbars, and prevents sleep. (A dedicated Pi appliance avoids needing this third-party app.)
  • Android TV: TV Bro is a solid open-source alternative for full-screen web apps on leanback devices.
Pro Tip: Most smart TVs have an "Auto Power Off" / "inactivity" timer. Disable it so the artwork doesn't stop after a few hours.
